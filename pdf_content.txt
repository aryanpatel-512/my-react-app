Sri Srinivasa Clean Rooms & Medical Furniture Web Application
Technical Evaluation and Development Action Plan
Document Purpose
This document defines the technical improvements required before the current application can be considered
production-ready.
The existing application provides a functional base for product management, category management, customer
inquiries, and administrative operations. However, the current implementation requires improvements in security,
backend architecture, database design, validation, exception handling, file management, testing, configuration, and
deployment practices.
The development team must implement the requirements listed in this document according to the assigned priority.

2. CRITICAL PRIORITY – BACKEND AUTHENTICATION AND
AUTHORIZATION
Current Observation
The application currently generates a JWT token after successful admin login.
The token is stored in browser localStorage as:
adminToken
The frontend admin dashboard checks whether this token exists and redirects the user to the login page when the
token is missing.
However, the backend administrative APIs currently do not verify the JWT token.
For example, operations related to:
•
Adding products
•
Updating products
•
Deleting products
•
Viewing inquiries
•
Deleting inquiries
•
Updating inquiry status
•
Updating inquiry priority
•
Adding inquiry notes
•
Adding categories
•
Updating categories
•
Deleting categories
can currently be accessed without JWT authorization at the API level.

Page 3
Checking the token only on the frontend is not a security mechanism.
A user can directly call the backend API without accessing the admin dashboard.
Required Implementation
Create a JWT authentication middleware.
Recommended file:
server/middleware/authMiddleware.js
The middleware must:
1
Read the Authorization header.
2
Verify the header uses the Bearer token format.
3
Extract the JWT token.
4
Verify the token using JWT_SECRET.
5
Reject missing tokens.
6
Reject invalid tokens.
7
Reject expired tokens.
8
Attach authenticated admin information to the request.
9
Call the next middleware only after successful verification.
Expected request format:
Authorization: Bearer <JWT_TOKEN>
Protected administrative routes must use the authentication middleware.
Example conceptual structure:
router.post("/", verifyAdminToken, createProduct)
The following operations must be protected:
•
POST product
•
PUT product
•
DELETE product
•
GET admin inquiries
•
PUT inquiry status
•
PUT inquiry priority
•
POST inquiry notes
•
DELETE inquiry
•
POST category
•
PUT category
•
DELETE category
Public routes should remain publicly accessible only where required.
Examples:

Page 4
•
GET products
•
GET product details
•
GET categories, if required by the public website
•
POST customer inquiry
Frontend Requirement
All admin API requests must send the JWT token.
The admin dashboard must include:
Authorization: Bearer ${token}
for every protected API request.
Acceptance Criteria
•
A protected API called without a token returns HTTP 401.
•
An invalid JWT returns HTTP 401.
•
An expired JWT returns HTTP 401.
•
A valid admin JWT allows the request.
•
Admin dashboard requests automatically include the token.
•
Expired sessions redirect the administrator to the login page.
Priority: CRITICAL
3. CRITICAL PRIORITY – ADMIN CREDENTIAL MANAGEMENT
Current Observation
Admin authentication currently compares the provided username and password directly with environment
variables.
The implementation follows the equivalent logic of:
username === ADMIN_USER
password === ADMIN_PASS
This means the authentication design depends on a plain credential comparison.
The backend dependencies include bcryptjs, but password hashing is not currently integrated into the login
process.
Required Implementation
Admin users should be stored in the database.
Create an Admin model.
Recommended file:
server/models/Admin.js
Recommended fields:
•
username
•
email

Page 5
•
passwordHash
•
role
•
isActive
•
lastLoginAt
•
createdAt
•
updatedAt
The password must never be stored as plain text.
Use bcrypt for password hashing.
Recommended minimum bcrypt salt rounds:
10 or 12
During login:
1
Find the admin by username or email.
2
Verify that the account exists.
3
Verify that the account is active.
4
Compare the submitted password using bcrypt.compare().
5
Generate the JWT only after successful authentication.
6
Update lastLoginAt.
7
Return a generic invalid credential message for failed authentication.
Do not reveal whether the username or password was incorrect.
Acceptance Criteria
•
Plain-text admin passwords are not stored.
•
bcrypt is used for password hashing.
•
bcrypt comparison is used during login.
•
Admin information is loaded from MongoDB.
•
Inactive admins cannot log in.
•
Login failures use generic messages.
Priority: CRITICAL

The environment file contained configuration keys for:
•

•

2
Add an explicit .env rule to .gitignore.
3
Create .env.example.
4
Remove sensitive configuration from repository history where required.
5
Rotate the MongoDB credentials.
6
Rotate the JWT secret.
7

The frontend required attribute is not sufficient because API requests can be sent directly to the backend.
Required Implementation
Implement backend request validation.
A validation library such as Joi, Zod, or express-validator may be used.
Product Validation
•
title – Required, string, trim whitespace, minimum length, maximum length.
•
price – Use an appropriate numeric representation if the value is an actual monetary amount; reject invalid
text and negative values.
•
category – Required and must reference or match a valid category.
•
description – Required with a maximum allowed length.
Inquiry Validation
•
name – Required, trimmed, and length restricted.
•
phone – Required if required by business rules; valid phone format and length restrictions.
•
email – Valid email format; normalize email and convert to lowercase where appropriate.
•
message – Required with minimum and maximum length.
•
type – Must use an allowed value.
Inquiry Status Validation
The status field must use an enum. Recommended values:
•
new
•
contacted
•
in_progress
•
closed
The backend must reject any unsupported status.

7. HIGH PRIORITY – GLOBAL EXCEPTION HANDLING
Current Observation
Almost every route currently contains its own try/catch block and returns the raw error message.
The repeated pattern creates duplicated code.
Returning error.message directly to clients may expose implementation or database information.
Required Implementation
Create a centralized error handling system.
Recommended files:
middleware/errorMiddleware.js
utils/ApiError.js
utils/asyncHandler.js

Page 11
The application should define a consistent error response.
{
  "success": false,
  "error": {
    "code": "PRODUCT_NOT_FOUND",
    "message": "Product not found"
  }
}
In production, stack traces and internal database errors must not be returned to the client.
Handle common errors including:
•
Invalid MongoDB ObjectId
•
Resource not found
•
Duplicate category
•
Validation failure
•
Unauthorized request
•
Forbidden request
•
Invalid JWT
•
Expired JWT
•
File upload failure
•
Database connection failure
•
Unexpected internal error
